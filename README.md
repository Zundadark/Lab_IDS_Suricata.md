# 🛠️ Развертывание Suricata IDS на Windows 11 и интеграция с Wazuh SIEM

**Статус:** Успешна завершена.
**Целевой хост:** Windows 11 24H2 (Сетевой мост / Bridged Network, IP: `192.168.3.46`)
**Атакующий хост:** Kali Linux (IP в той же подсети `192.168.3.50`)
**SIEM-Менеджер:** Ubuntu Server (IP: `192.168.3.49`)

## 🏗️ ЭТАП 1: Подготовка полигона и зачистка хоста

Изначально на Windows-хосте активно работал Sysmon с кастомным конфигом логирования сети (Event ID 3), что создавало избыточный информационный шум (False Positives) на дашборде Wazuh (уровни алертов 12–15 на Shim-базы Windows и дропы временных файлов). Для создания «чистого листа» перед развертыванием IDS я решил остановить сетевой аудит.

1. Попытка стандартной остановки службы из CMD от имени Администратора:
   ```cmd
   net stop sysmon64
   ```
   *Результат:* Ошибка `Системная ошибка 5. Отказано в доступе`. Сработал механизм самозащиты драйвера ядра Sysmon (Tamper Protection).
2. Полная выгрузка драйвера и удаление службы через собственный движок Sysinternals:
   ```cmd
   sysmon64.exe -u
   ```
   *Результат:* Успешно. Служба `Sysmon64` и драйвер ядра `SysmonDrv` полностью удалены. Поток логов в канале `Microsoft-Windows-Sysmon/Operational` прекращен.

## 💾 ЭТАП 2: Поэтапное развертывание Suricata на Windows 11

1. **Установка движка:** Скачан и запущен официальный Windows-установщик `Suricata-8.0.6-64.msi`. Установка произведена в корневой каталог по умолчанию: `C:\Program Files\Suricata`.
2. **Установка драйвера перехвата пакетов:** При первом запуске `Suricata.exe` возникла ошибка: `Система не обнаружила wpcap.dll`.
   * *Решение:* Скачан и установлен официальный драйвер **Npcap** (npcap.com). В процессе установки принудительно активирован чекбокс **"Install Npcap in WinPcap API-compatible Mode"** для генерации библиотеки `wpcap.dll`.
3. **Создание структуры директорий:** Внутри рабочего каталога `C:\Program Files\Suricata\` вручную созданы папки для баз сигнатур и хранения журналов:
   ```cmd
   mkdir rules
   mkdir log
   ```
4. **Написание кастомной сигнатуры:** В каталоге `rules\` через Блокнот от Администратора создан файл `suricata.rules`. В него внесено кастомное правило для обнаружения TCP SYN-сканирования от Nmap:
   ```text
   alert tcp any any -> any any (msg:"ATTACK Nmap Scan Detected"; flags:S; sid:1000001; rev:1;)
   ```

## 🏆 ЭТАП 5: УСПЕШНОЕ РЕШЕНИЕ ПРОБЛЕМ И ЗАВЕРШЕНИЕ РАБОТЫ

В ходе финального теста удалось найти и исправить все ошибки, из-за которых логи не доходили из Suricata в Wazuh. Сейчас всё работает стабильно и в реальном времени.

### 🔍 Почему логи не шли в прошлый раз (Главная причина):
Первоначально агент Wazuh горел зеленым статусом `Active`, но упорно не видел логи от Suricata. Причина оказалась в **особенности работы Windows с файлами (Блокировка файла)**. 

Когда мы запускали Suricata, она открывала файл `eve.json` для записи и полностью блокировала его для других программ. Агент Wazuh пытался прочитать этот файл, но Windows выдавала ему отказ в доступе. Логи писались, агент работал, но связи между ними не было, потому что операционная система не разрешала им использовать файл одновременно.

### 🛠 Как мы решили сопутствующие проблемы в процессе дебага:

1. **Починили сервер Wazuh (Ubuntu):** 
   Во время агрессивных тестов сервер на Ubuntu упал в синий экран (Kernel Panic) из-за конфликта виртуального звука в VirtualBox. Мы перезагрузили сервер в режиме восстановления, убедились, что служба `wazuh-manager` жива, и выделили виртуалке больше ресурсов процессора.
   
2. **Сбросили старые ключи (Ошибка Duplicate Agent):**
   Из-за частых перезапусков систем сервер Wazuh запомнил старый ключ авторизации нашего компьютера и не пускал его снова, выдавая ошибку дубликата имени. Мы зашли в консоль Ubuntu и вручную удалили старую запись:
   ```bash
   sudo /var/ossec/bin/manage_agents -r 001
   sudo systemctl daemon-reload
   sudo systemctl restart wazuh-manager
   ```
   После этого Windows-агент успешно подключился заново и получил чистый, рабочий ключ.

3. **Исправили ошибки в конфигах:**
   - В файле правил `suricata.rules` исправили синтаксис (добавили обязательную точку с запятой `;` в конце правила). Движок успешно запустился.

### 🎯 ПРОВЕРКА РЕЗУЛЬТАТОВ И ТЕСТИРОВАНИЕ АТАК:

Когда мы запустили программы в правильном порядке, агент Wazuh получил доступ к файлу, и его статус на дашборде сменился на **Active**.

# Разворачиваем Suricata IDS на Linux и подключаем к Wazuh

**Дата:** 23 августа 2026
**Стенд:** Ubuntu Server (wazuh-server, 192.168.3.49) в VirtualBox, бридж-сеть
**Цель:** поставить сетевой сенсор Suricata рядом с уже работающим Wazuh, научить его детектить Nmap-сканирование и увидеть алерт на дашборде Wazuh.

---

## Зачем это вообще нужно (коротко для себя)

Wazuh сам по себе — это **SIEM** (система, которая собирает логи с разных источников и решает, что из этого тревога, а что нет). Но Wazuh не видит сетевой трафик напрямую — он читает логи. Чтобы получить алерты про сканирование портов, атаки в сети и т.п., нужен отдельный **сетевой сенсор** — программа, которая реально смотрит на пакеты, летящие по проводу. Это и есть Suricata — **IDS** (Intrusion Detection System, система обнаружения вторжений).

Схема в итоге получилась такая:

```
Сетевой трафик → Suricata (смотрит пакеты, матчит правила) → eve.json (файл с алертами)
                                                                        ↓
                                                    Wazuh читает файл → создаёт alert на дашборде
```

---

## Шаг 1. Установка Suricata

Ставили из **PPA** (Personal Package Archive — отдельный репозиторий с более свежими версиями пакетов, чем стандартный Ubuntu-репозиторий):

```bash
sudo add-apt-repository ppa:oisf/suricata-stable
sudo apt update
sudo apt install suricata -y
```

Получили версию **8.0.6** — свежую.

**Важный момент:** при установке пакет сам создал системного пользователя `suricata` (не для логина, а просто чтобы процесс работал не от root, а от отдельного ограниченного пользователя — это правило безопасности "принцип наименьших привилегий"). У него нет домашней директории — это нормально, демонам она не нужна.

---

## Шаг 2. Выбор сетевого интерфейса

Командой `ip a` посмотрели, какие сетевые интерфейсы есть на машине:

- **`lo`** — виртуальный "интерфейс самого себя" (`127.0.0.1`), трафик через него никогда не покидает машину.
- **`enp0s3`** — рабочая сетевая карта с реальным IP `192.168.3.49`, статус `UP` — её и используем.
- **`enp0s8`** — второй адаптер, добавленный в VirtualBox, но выключен (`DOWN`), не используется.

Указали Suricata слушать именно **`enp0s3`** в конфиге `/etc/suricata/suricata.yaml`, секция `af-packet`. `af-packet` — это способ, которым Suricata на Linux получает доступ к сырым пакетам напрямую с сетевой карты, в обход обычной обработки ядром (обычные программы такого доступа не имеют — они видят только трафик, адресованный им самим).

---

## Шаг 3. Первое правило детекта

Правила Suricata хранятся в отдельных `.rules` файлах. Создали `local.rules` со своим первым правилом:

```
alert tcp any any -> any any (msg:"ATTACK Nmap SYN Scan Detected"; flags:S; sid:1000001; rev:1;)
```

### Разбор синтаксиса по частям:

| Часть | Что значит |
|---|---|
| `alert` | Действие при совпадении — залогировать. (Альтернативы: `drop` — заблокировать, работает только в IPS-режиме; `pass` — пропустить.) |
| `tcp` | Протокол, который проверяем. |
| `any any -> any any` | src_ip src_port → dst_ip dst_port. `any` = любой. Стрелка — направление трафика. |
| `msg:"..."` | Текст, который увидим в алерте — просто для читаемости. |
| `flags:S` | Проверка TCP-флагов в заголовке пакета. `S` = только флаг SYN установлен (это первый пакет в любом TCP-соединении, а у Nmap SYN-скана после него никогда не идёт полноценный ACK). |
| `sid:1000001` | Уникальный номер правила. Диапазон 1–1000000 зарезервирован под официальные правила, свои всегда начинают от 1000000. |
| `rev:1` | Версия правила — увеличивается при каждой правке логики. |

**Важная оговорка, которую я понял по ходу:** правило `flags:S` без ограничений ловит **любой** SYN-пакет, а не только сканирование — обычный запрос браузера тоже начинается с SYN. На реальном трафике (не в тестовой лабе) такое правило будет шуметь чудовищно. Для настоящего детекта сканирования нужен `threshold` — счётчик, который считает, сколько раз что-то произошло за отрезок времени, и алертит только при превышении:

```
alert tcp any any -> any 22 (msg:"SSH Bruteforce Attempt"; flow:to_server; threshold:type threshold, track by_src, count 5, seconds 60; sid:1000002; rev:1;)
```

Это правило сработает только на 6-й попытке за минуту с одного источника — а не на каждом отдельном пакете.
Однако в данной лабе threshold использоваться не будет.

## Шаг 4. Грабли с путями (самая долгая часть)

Тут поймал целую цепочку последовательных проблем — каждая тянула следующую:

1. **`Directory '/etc/suricata/rules' does not exist`** — оказалось, в новых версиях пакета (из PPA) правила по умолчанию лежат не в `/etc/suricata/rules/`, как в старых мануалах, а в **`/var/lib/suricata/rules/`**. Путь берётся из параметра `default-rule-path` в конфиге.

2. **Даже правильная директория не существовала физически** — пакет её не создаёт заранее, она появляется только после первого запуска `suricata-update` (утилита, которая скачивает готовый набор правил Emerging Threats — тысячи сигнатур на известные атаки, эксплойты, вредоносное ПО и т.д.). Создал вручную:
   ```bash
   sudo mkdir -p /var/lib/suricata/rules
   sudo chown suricata:suricata /var/lib/suricata/rules
   ```

3. **Не было файла `suricata.rules`**, на который ссылался конфиг (`rule-files:`), потому что `suricata-update` ещё ни разу не запускался. Временно закомментировал строку, протестировал конфиг только со своим `local.rules`, потом запустил:
   ```bash
   sudo suricata-update
   ```
   После этого появился `suricata.rules` (~45 МБ, 52 552 готовых правила) и обе строки в конфиге заработали вместе.

4. **`unix-manager: failed to create socket directory /var/run/suricata/`** — процессу не хватало прав создать директорию для управляющего сокета (нужен для утилиты `suricatasc`, не критично для самого детекта, но лучше починить):
   ```bash
   sudo mkdir -p /run/suricata
   sudo chown suricata:suricata /run/suricata
   ```

**Вывод, который стоит запомнить:** когда команда выдаёт "No such file or directory" — не всегда дело в правах доступа (`chown`/`chmod`), иногда самой директории физически не существует, и её нужно создать (`mkdir -p`) прежде чем что-то туда писать.

---

## Шаг 5. Тест конфига перед запуском

Прежде чем запускать как постоянный сервис, стоит проверить конфиг флагом `-T` (test mode — проверяет всё без реального запуска):

```bash
sudo suricata -T -c /etc/suricata/suricata.yaml -v
```

Финальный чистый результат:
```
Info: detect: 2 rule files processed. 52552 rules successfully loaded, 0 rules failed, 0 rules skipped
```

Отдельно разобрали флаг **`-S <файл>`** — он подменяет весь список правил на один указанный файл, полезен для разового теста из консоли, но **не подходит** для сервиса, который стартует через `systemctl` — там нужно, чтобы всё было прописано именно в `suricata.yaml`, иначе при следующем автоматическом старте (например, после перезагрузки сервера) флаг просто не применится.

---

## Шаг 6. Запуск как сервис

```bash
sudo systemctl enable suricata   # чтобы стартовал автоматически при загрузке системы
sudo systemctl start suricata
sudo systemctl status suricata   # проверка, что живой
```

**Грабли:** после того как починил `/run/suricata` (шаг 4.4), забыл сделать `systemctl restart` — старый процесс (с ещё не загруженными правилами) продолжал висеть с тем же **PID** и временем старта. Проверка по `Main PID` и `Active: ... since` в выводе `systemctl status` — хороший способ убедиться, что изменения конфига реально применились, а не просто "команда выполнилась без ошибок".

---

## Шаг 7. Подключение к Wazuh — тоже не с первого раза

Файл с алертами Suricata (`eve.json`) сам по себе никуда не передаётся — нужно явно сказать Wazuh его читать. Это делается в главном конфиге Wazuh:

```bash
sudo nano /var/ossec/etc/ossec.conf
```

Добавить перед закрывающим тегом `</ossec_config>`:
```xml
<localfile>
  <location>/var/log/suricata/eve.json</location>
  <log_format>json</log_format>
</localfile>
```

```bash
sudo systemctl restart wazuh-manager
```

**Грабли:** я про этот шаг просто забыл — потратил время, разбирая, почему Wazuh "не видит" события, хотя причина была в том, что его никто и не просил их читать.

### Как проверяли по цепочке, где обрыв

Когда алертов на дашборде не было, важно было понять — обрыв на каком именно этапе: Suricata не детектит, Wazuh не читает файл, или читает, но не может классифицировать?

1. **Растёт ли `eve.json` вообще?**
   ```bash
   sudo tail -f /var/log/suricata/eve.json
   ```
   Если строки появляются — Suricata видит трафик и пишет.

2. **Читает ли Wazuh уже добавленный файл?**
   ```bash
   sudo grep -i suricata /var/ossec/logs/archives/archives.log | tail -5
   ```
   `archives.log` — это файл, куда Wazuh пишет **вообще все** полученные логи, даже если ни одно правило алерта не сработало. Если тут есть записи — значит передача файла работает, просто нет "распознавания" под конкретное содержимое.

3. **Есть ли вообще настоящие alert-события от Suricata, а не просто фоновый трафик?**
   ```bash
   sudo grep '"event_type":"alert"' /var/log/suricata/eve.json | tail -3
   ```
   Тут поймал забавный самообман: раньше делал `grep alert` и находил совпадения — но это было поле `"alerted":false` у обычных flow-событий (означает "по этому потоку алерта не было"), а не настоящий alert. Нужно искать точно `"event_type":"alert"`.

## Что взять с собой на будущее (шпаргалка)

- **`ip a`** — посмотреть сетевые интерфейсы, IP-адреса, статус (`UP`/`DOWN`).
- **`sudo suricata -T -c /etc/suricata/suricata.yaml -v`** — тест конфига без реального запуска, безопасно проверять перед `restart`.
- **`sudo systemctl status <сервис>`** — всегда проверять `Main PID` и время `Active: ... since` после конфиг-правок, чтобы убедиться, что сервис реально перезапустился, а не продолжает работать со старыми настройками.
- **Дефолтные пути правил Suricata могут отличаться в зависимости от источника пакета** — не доверяй слепо старым мануалам, сверяйся с `default-rule-path` в собственном `suricata.yaml`.
- **`suricata-update`** — обязательно запустить хотя бы раз, чтобы получить готовый набор сигнатур ET (Emerging Threats), а не только свои собственные правила.
- **`sudo grep ... /var/ossec/logs/archives/archives.log`** — способ проверить, что именно Wazuh получает "на входе", даже если на дашборде пусто (дашборд показывает только то, для чего сработало правило).
- **`flags:S` без `threshold` — шумное правило.** На проде почти всегда нужна связка с `threshold:type threshold, track by_src, count N, seconds M`, чтобы алертить не на каждый отдельный пакет, а на аномальную частоту.
